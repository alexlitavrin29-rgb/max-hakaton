# Ограниченный нагрузочный прогон

28.09.2026 на VPS проверяли предыдущую техническую редакцию кода: 30 минут
устойчивой нагрузки и 10 минут всплеска, всего **11 040 запросов** четырёх
синтетических аккаунтов. Сообщений MAX не отправляли, тестовые данные удалили.
Это измерение до выпуска r5; оно не доказывает его длительную доступность.

| Операция | Устойчиво: запросы / p95 | Всплеск: запросы / p95 |
|---|---:|---:|
| `/api/health` | 1800 / 41,45 мс | 2400 / 187,87 мс |
| Поиск помощи | 360 / 124,36 мс | 1200 / 151,96 мс |
| Защищённое чтение | 1440 / 615,81 мс | 2400 / 667,51 мс |
| Защищённая запись | 240 / 747,72 мс | 480 / 786,93 мс |
| Действие диалога | 240 / 647,92 мс | 480 / 682,83 мс |

Тайм-аутов не было. Во всплеске поиск помощи дал один транспортный сбой из
1200 запросов. Записи одного аккаунта получили 20 ответов 429 из 240 в
устойчивой фазе и 33 из 480 во всплеске; это ограничение одновременных
действий одного аккаунта. Остальные группы ответили 200. Во время прогона
перезапускали один из двух экземпляров. Монитор собрал 260 отсчётов с
интервалом 10 секунд; максимум CPU miniapp — 109,92%, памяти — 363,1 МиБ.

После этого прогона оптимизировали чтение «Моего»: отдельный повтор 200
запросов при параллельности 4 дал p95 11,43 мс вместо 391,33 мс до
изменения; все 400 запросов двух сравнительных замеров завершились 200.
Последующие изменения r5 проверены функционально и на двух экземплярах, но
такого же 40-минутного замера для них не проводили. Эти числа не являются SLA.

Обезличенные исходные итоги: [запросы](load-results.json) и
[монитор](load-monitor-summary.json). Повторяемый сценарий:
`tools/submission/load_check.py`; запускать его следует только в отдельном
контролируемом окружении с тестовыми аккаунтами.
