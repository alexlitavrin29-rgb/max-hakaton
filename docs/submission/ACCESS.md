# Доступ и тестовые данные

## Публичные операции

`GET /api/health`, `/api/info` и четыре маршрута `/api/help/*` не требуют
учётной записи. Тестовый город: Казань, регион: Татарстан. DATA-API получает
настоящий ID из первой страницы и открывает карточку. ID не зашит в проверку.
`limit=101` проверяет отказ с HTTP 422.

## Роль user

Сервис использует вход MAX, а не собственный логин и пароль:

1. Открыть `https://max.ru/t143_hakaton_max_bot` отдельным тестовым аккаунтом
   MAX, затем мини-приложение.
2. Клиент отправляет подписанные MAX `init_data` в `POST /api/session`.
   Сервер проверяет подпись и время. Ответ: `{"session":"…"}`.
3. Использовать `Authorization: Bearer <session>` для роли `user`.
   Сеанс живёт до часа бездействия и переживает перезапуск приложения.
   Bearer действует на экземплярах miniapp с общей PostgreSQL и отзывается
   при удалении аккаунта.

Организаторам нужно отдельно передать доступ к тестовому аккаунту либо
согласовать выдачу свежего сеанса непосредственно перед проверкой.
Токен бота передавать жюри для этого не нужно. Секреты не включаются в архив,
DATA-API и презентацию. Используйте защищённый канал организаторов.

Для приложенного исполнителя передайте сеанс через переменную окружения
`DATA_API_SESSION` и выполните:

```sh
python tools/submission/check_api.py --full --output api-check-full.json
```

Защищённые проверки открывают три раздела, читают «Моё», сохраняют ответ
`exit_docs`, затем удаляют это сохранение через cleanup даже при ошибке.
На выделенном аккаунте этого ответа не должно быть в «Моём» до прогона.
Между разными `/api/action` нужен интервал ≥0,5 с. Для безопасного повтора
после сетевого обрыва передавайте тот же `Idempotency-Key`. DATA-API 1.0 не
содержит поля задержки; приложенный исполнитель делает её сам.

Кнопка «Удалить сохранения и напоминания» в «Моём» вызывает защищённый
`DELETE /api/account`: записи текущего MAX ID удаляются из рабочей БД,
сеансы miniapp этого ID закрываются. Используйте только выделенный тестовый
аккаунт; операция затронет все его сохранения и напоминания. Существующие
резервные копии остаются, как указано в [DATA-POLICY.md](DATA-POLICY.md).

Проверки входов в работу/жильё не доказывают качество живой выдачи. Для неё
нужен ручной сценарий PRODUCT.md с доступными провайдерами. Объявления
меняются и могут отсутствовать, поэтому их ID не зафиксированы в DATA-API.

## Два режима

- Локальный Compose: preview на 127.0.0.1:18866 с общей личностью `preview`.
  `POST /api/session` с `{}` создаёт сеанс без реальных секретов. Проверки
  production-mode и reject-unsigned-launch здесь намеренно не проходят.
- VPS: `MINIAPP_PREVIEW=0`, только подписанный MAX-вход. Это целевой режим
  DATA-API.yaml. Владелец подтвердил работу приложения на телефоне;
  серверные синтетические проверки подписи приведены отдельно.

## Данные в архиве

`submission/scenario.json` содержит тексты и переходы публикации 9, 457 узлов,
включая отключённые исторические узлы. `rules.child_only` закрывает взрослые
входы. `project/llm/data/help_points.json` содержит 364 точки помощи,
`saved_answers.json` — реестр 117 сохраняемых материалов. Пользовательские
таблицы, переписки, сохранения и дампы БД не включены.
Ограниченный набор исторических синтетических данных в `docs/test-results`
и `docs/quality-acceptance` нужен для воспроизведения существующих тестов.
