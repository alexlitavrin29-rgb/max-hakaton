# COV — контракт передачи между облачными исполнителями

Идентификаторы заданий — COV-01…COV-06; метки контрольных точек — COV-A…COV-E. Старые ключи gates.K1…K5 читаются по таблице в `00-common.md`, не как названия задач.

Это формат рабочих отчётов, а не новая подсистема продукта. Не добавляй серверную базу или универсальный оркестратор ради этих файлов.

## Состояние этапов

Файл: `docs/implementation/planner-coverage/PROGRESS.json`. На момент публикации облачного пакета COV-01 уже `integrated`, COV-02…COV-06 — `pending`, `active_stage=null`. Подготовка заданий не закрывает им COV-A. Единственный реестр прогресса сохраняется по этому пути.

Исполнитель назначенного этапа устанавливает `active_stage` и `implementing` после проверки зависимостей. Для N>1 требуется завершённый COV-E этапа N−1 с проверяемым отчётом интеграции. Одновременно допускается только один начатый незавершённый этап. История `integrated` не считается активной.

| Точка | Доказательство | Кто закрывает |
|---|---|---|
| COV-A | Проверенные обязательные материалы, источники, точные контракты и кейсы | Исполнитель |
| COV-B | Целевые ошибки воспроизведены до исправления; уже работающие случаи честно выделены | Исполнитель |
| COV-C | Реализация, необходимые проверки, фактические ответы и коммит готовы | Исполнитель |
| COV-D | Независимый review конкретного продукта одобрен | Проверяющий |
| COV-E | GitHub и сервер обновлены, установленный путь проверен | Интегратор |

Закрывать только последовательные точки. Процент = 20 × число закрытых точек; отдельное поле процента не хранится, чтобы оно не расходилось с контрольными точками. Число интегрированных этапов = количество этапов с `status=integrated` и COV-A–COV-E=true.

Переходы: `pending → implementing → ready_for_review → approved → integrating → integrated`. От review допустим `needs_changes → ready_for_review`. `active_stage` остаётся выбранным при исправлениях и частичной интеграции; после COV-E становится null. Следующий этап сам назначает себя после проверки зависимости. При несовпадении `active_stage`, статуса и отчётов устранить противоречие по доказательствам, не выбрать удобный вариант.

## Файлы каждого этапа

Папка `docs/implementation/planner-coverage/stage-NN/`, NN = 01–06:

- SOURCES.md: утверждение → прямая ссылка → дата проверки → условия → проверено/спорно/отложено. Для ранее принятого материала допустима ссылка на прежнюю запись с новой датой проверки.
- MATERIALS.md: ID, ситуация, аудитория, территория, краткий текст, действия, препятствия, источники, ограничения, видимость в интерфейсах.
- CONTRACT.md: точные категории/вопросы/материалы/действия, типы полей, состояния и переходы. Указать обратную совместимость и блокировку преждевременного плана.
- CASES.json (этап 1) либо CASES.md (остальные): синтетические входы, последовательность уточнений, ожидаемые состояния, допустимые ID/действия и запрещённое поведение.
- TESTS.md: команды, окружение без секретов, red/green, что было пропущено и почему; никаких вымышленных результатов.
- RESULTS.md: фактические запросы и ответы программы с действиями/ссылками и оценкой. Пустой шаблон не закрывает COV-C.
- REPORT.md: объём изменений, покрытие требований, ограничения, спорные решения, следующий шаг и фактический прогресс.
- HANDOFF.json: краткое состояние для следующего агента по шаблону ниже.
- REVIEW.md: независимая проверка. Повторные проверки сохранять разделами с датой/SHA, не стирать прежние замечания.
- INTEGRATION.md: фактический выпуск, его версия, резерв/откат и проверки. До интеграции файл не должен изображать состоявшийся выпуск.

## Коммиты без противоречия собственному SHA

1. В `base_sha` запиши HEAD до изменений продукта этого этапа; проверь, что он содержит результат предыдущего этапа. Не используй исходный SHA пакета для каждого нового этапа.
2. Зафиксируй продукт, тесты и готовые материалы. Полученный SHA — `implementation_sha`. Не пытайся вписать SHA коммита внутрь самого этого коммита.
3. HANDOFF.json и записи о результатах можно зафиксировать следующим отчётным коммитом. После `implementation_sha` разрешены только отчётные изменения в `docs/implementation/planner-coverage/stage-NN/` и `docs/implementation/planner-coverage/PROGRESS.json`. Даже там изменение требований/контракта или ожидаемых результатов, меняющее смысл приёмки, требует повторной содержательной проверки, а не формальной ссылки на «только документацию».
4. Проверяющий проверяет продукт `implementation_sha` и актуальные доказательства; при одобрении устанавливает `reviewed_sha=implementation_sha`. Его отчёт может быть следующим коммитом. Diff вне разрешённых отчётных путей после проверенного SHA обязан быть пустым.
5. Интегратор выбирает существующий коммит `release_sha`, содержащий этот продукт и принятые отчёты. Доказывает отсутствие изменений продукта между `reviewed_sha` и `release_sha`; записывает обе версии. Следующие отчёты об установке не меняют фактический `release_sha` продукта.
6. Новая правка продукта после review: новый `implementation_sha`, COV-D/COV-E=false, `reviewed_sha=null`, `release_sha=null` для новой попытки. Сведения о прежней установке сохранять в истории INTEGRATION.md; не стирать факт, что старая версия уже могла быть опубликована.

Отчётная папка не исключается из проверки содержания. Секреты, персональные данные и сырые пользовательские переписки в неё не попадают. Git diff/status всегда проверяются вместе с SHA.

## HANDOFF.json: шаблон нового задания COV-02

Заменяй значения только фактами. `null` означает «ещё нет», а не успешную проверку. Для других заданий меняются id, stage и paths. Ключи gates в JSON оставлены совместимыми; отображение COV-A…COV-E см. в `00-common.md`.

```json
{
  "schema_version": 1,
  "program_id": "COV",
  "id": "COV-02",
  "stage": 2,
  "status": "implementing",
  "base_sha": null,
  "implementation_sha": null,
  "reviewed_sha": null,
  "release_sha": null,
  "gates": {"K1": false, "K2": false, "K3": false, "K4": false, "K5": false},
  "report": "docs/implementation/planner-coverage/stage-02/REPORT.md",
  "review_artifact": null,
  "integration_artifact": null,
  "blocking_issues": [],
  "limitations": [],
  "next_action": "COV-A: подготовить проверенные материалы и контракт"
}
```

Статус, gates и SHA должны совпадать с записью этапа в PROGRESS.json. Не закрывай точку при неполном обязательном результате. Если окружение блокирует тест, укажи конкретную причину и какой результат не проверен.

## Формат кейса и фактического результата

Для CASES.json этапа 1 используй массив объектов: `id`, `input`, `steps`, `expected_state`, `allowed_material_ids`, `required_conditions`, `forbidden_behaviors`. Точные ID заполняются в COV-A после определения каталога. Непроверенный ID не становится допустимым по одному упоминанию в тесте.

Для каждой записи RESULTS.md:

```text
Кейс / дата / SHA:
Тип: deterministic | mock | replay | live
Вход и последовательность действий пользователя:
Ответ API: статус, question_id, choices, information, tasks/план (без секретов).
Отображённый пользователю текст, действия, ссылки:
Ожидание и результат: passed / failed / not_run.
Недочёт и решение либо ограничение проверки:
Доказательство: команда/файл/скриншот синтетического сеанса.
```

В mock укажи, что подменено; в replay — происхождение сохранённого синтетического ответа; в live — модель, количество вызовов и согласованный бюджет без ключей. Не называй ответ модели фактическим ответом всей программы, если не проверены серверная обработка и отображение. При ограничении на живые вызовы это отражается в review, а не скрывается.

## Короткий ответ владельцу

«COV-NN: X% — закрыты точки COV-…; интегрировано Y из 6. Что изменилось: … Проверено: … Ограничения: … Следующий промпт: …»

Приложи ссылки на REPORT/RESULTS, а для выпуска — GitHub и INTEGRATION. Процент показывает пройденные точки, не объём оставшейся работы и не точность ИИ.
