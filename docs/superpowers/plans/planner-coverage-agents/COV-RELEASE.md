# COV-RELEASE — публикация проверенного задания

Работай только с программой `COV`: проверь `program_id`, `id` задания и `active_stage` в PROGRESS.json. Используй фактический checkout облачного репозитория. Контрольные точки COV-A–COV-E сопоставляются с прежними ключами JSON по `00-common.md`.

Этот промпт выполняет назначенный владельцем интегратор с разрешёнными доступами. Сам пакет не передаёт SSH-ключи или секреты. Если в облаке доступа к VPS нет, подготовь точный handoff и сохрани COV-E=false; не ищи ключи на компьютере владельца и не выдавай GitHub/PR за установку.

Интегрируй проверенный этап проекта «Точка опоры» на GitHub и действующий сервер, затем проверь установленную версию. Прочитай применимые AGENTS.md, если они есть в checkout, `00-common.md`, `10-handoff.md`, ТЗ, PROGRESS.json, HANDOFF.json, REVIEW.md и текущую документацию развёртывания. Это отдельное задание на публикацию; не начинай следующий этап.

## 1. Проверка версии и допуска к выпуску

- `active_stage` должен указывать на единственный активный этап со статусом `approved`, COV-A–COV-D=true. При возобновлении допустим `integrating`, но сначала установи фактический результат прошлой попытки; не повторяй публикацию/миграцию вслепую.
- Проверь COV-E предшествующего этапа, `reviewed_sha == implementation_sha`, REVIEW.md и отсутствие блокирующих замечаний. Критичные непроверенные условия не обходить.
- Проверь Git status, HEAD и diff после `reviewed_sha`. Допустимы только отчётные изменения, перечисленные в `10-handoff.md`. Если изменён продукт, верни на исполнителя/проверку, сбросив COV-D/COV-E. Не включай посторонние файлы или чужие правки.
- Выбери `release_sha` после фиксации отчётных документов. Запиши, каким diff доказано равенство продукта проверенной версии. Все последующие runtime-изменения требуют новой проверки.
- Проверь актуальные remotes и согласованную ветку назначения. В исходной копии `github` — GitHub, `origin` — локальный bundle; имя само по себе не подтверждает адрес. Не делай force push, не угадывай main и не создавай новую стратегию выпуска. Если цель действительно не установлена из проекта и переписки, уточни только её.

## 2. Подготовка сервера и отката

- Прочитай `project/deploy/README.md` и последний INTEGRATION.md. Сними текущий состав сервисов, версии образов/файлов, активную публикацию/черновик, важные флаги и состояние health. Старый номер публикации не использовать как предположение.
- На исходном окружении известен сервер `135.106.229.210`, каталог `/opt/tochka`, Compose `/opt/tochka/project/deploy/compose.yml`. Это ориентиры для проверки, а не разрешение перезаписать другое окружение. Используй существующий SSH-доступ, не выводи ключи и `.env`.
- Сохрани резерв затронутых файлов/конфигурации и метаданные предыдущих образов. Для изменения данных нужен соответствующий проверяемый резерв и план миграции. Зафиксируй путь и проверку читаемости/целостности резерва до установки.
- Опиши точный откат кода. Не восстанавливай старую БД поверх новых пользовательских записей автоматически. Сценарий меняй только точечным patch к проверенной актуальной версии; не заливай `submission/scenario.json` целиком.
- Составь перечень изменённых runtime-файлов/данных и сервисов, которые их используют. Общий модуль может требовать пересборки нескольких сервисов. Не выполняй unrelated обновления зависимостей или платформы.

## 3. Выпуск

- Поставь `integrating`. Выполни предусмотренные проектом предрелизные проверки на выбранном `release_sha`, используя сохранённые результаты review и новые проверки только там, где требуется свежесть/новое окружение.
- Отправь коммит в установленную GitHub-цель. Проверь удалённый SHA через Git и зафиксируй ссылку на коммит. При создании PR прикрепи его к текущей задаче; PR сам по себе не доказывает установку на сервер.
- Разверни именно этот продукт штатным способом. Сопоставь файлы/хеши и образы сервера с `release_sha`; серверный checkout не обязателен, но происхождение runtime должно быть доказуемо.
- При необходимости изменения сценария сначала проверь предусловия patch, затем сохрани новую версию и точный diff. Конфликт с более свежей публикацией требует анализа, не перезаписи.
- Не считать успехом только код завершения SSH, push или сборки. При ошибке останови дальнейшие изменения, установи фактическое состояние, при необходимости выполни подготовленный откат кода и проверь его.

## 4. Проверка установленного пути

- Сервисы healthy; проверенный материал присутствует в каждом использующем его сервисе; публикация, `child_only` и нужные флаги сохранены.
- Подписанный синтетический HTTP-сеанс проходит основной сценарий этапа, нужное уточнение, выбор приоритета, открытие карточки/ссылки и действия с планом. Проверь изоляцию тестового пользователя; очисти только созданные тестовые записи.
- Повтори существенный отрицательный сценарий и прежний рабочий маршрут: нет плана до выбора, ложного «AI недоступен» из-за темы и нового тупика. Срочный подготовленный путь проверь без запроса к провайдеру.
- Если проверка требует платного вызова, используй только актуально разрешённый остаток. При его отсутствии не обходи это реальным скрытым вызовом; укажи незакрытую проверку. Для непройденной обязательной проверки COV-E=false.
- Для этапа 6 проверь опубликованный движок с подменой отправки MAX, навигацию и одинаковые факты материалов. Не отправляй настоящие сообщения пользователям. Отдельно укажи пределы проверки native MAX/WebView.
- По доступности проверь внешний HTTPS и браузерный путь. Недоступность с проверяющей машины объясни отдельно; не называй внешний пользовательский путь проверенным только по health контейнера.

## 5. Отчёт и завершение

Создай INTEGRATION.md: время, baseline сервера, `reviewed_sha`, `release_sha`, GitHub-ссылка/ветка/удалённый SHA, резерв, команды установки без секретов, изменённые сервисы/образы/хеши, версии сценария до/после, результаты проверок и ограничения, точный план отката.

Только после подтверждения GitHub, серверного runtime и обязательных проверок: COV-E=true, статус `integrated`, `active_stage=null`, 100%. В HANDOFF.json/PROGRESS.json укажи `release_sha` и путь отчёта. Отчёт о состоявшемся выпуске можно закоммитить и отправить отдельным документационным коммитом: он не меняет установленный `release_sha` продукта.

Если GitHub обновлён, а сервер или проверка не завершены: COV-E=false, 80%, статус `integrating`, точный частичный результат и препятствие. Не начинать следующий этап. Не скрывать откат или незавершённость за словом «готово».

Финальный ответ: что стало доступно пользователю, SHA и ссылка GitHub, что установлено и проверено на сервере, ограничения, прогресс и какой этап можно выдавать следующим.
